# 从提出需求到完成项目：可复用的 Agent 工作流程

下面整理的是本项目形成的方法，不是原始聊天逐字记录。大量沟通集中在真实测试现象、策略选择和验证上；这里保留有效步骤，省去重复讨论。开发使用 Codex，学生负责提出目标、选择策略方向、观察运行和提交评测，Agent 负责读取实现、提出方案、编写修改及辅助分析。是否达到目标由运行证据判断。

## 1. 先把任务边界说完整

最初就告诉 Agent：项目在哪、只能改哪些文件、如何获胜、哪些情况失败、你希望它先了解还是立刻编码、现在是否允许运行。对本项目，“只能改 `UsrAI.cpp` 和 `UsrAI.h`”比“提高胜率”更具体，能避免 Agent 从引擎或配置上绕过题目。

先读代码和文档，让它解释状态快照、指令提交、成本、科技前置、寻路和胜负条件。不要把泛用的帝国时代经验直接套入课程引擎。明确哪些判断已从代码确认，哪些还需要实验。

## 2. 写下可执行的规划

规划应覆盖经济、科技、防守、反攻与转化收尾，而不是只有“多造弓兵”。每个模块写清输入、状态、优先级、失败恢复和与其他模块共享的资源。安排最小编译里程碑，再逐步建立完整行为。

把修改权限、接口约定和常见陷阱放进 `AGENTS.md`；把跨项目也可复用的 RTS 调试方法做成 skill。当前仓库附带的项目 skill 是在经验整理时提炼的新工具，并非所有开发阶段都已经使用它。

## 3. 让 Agent 完成一个闭环

一次任务最好能落到具体可检查的结果：理解接口 → 修改代码 → 完成允许的检查 → 说明行为变化。若明确要求“只编译、不运行”，检查就到构建结束；若要求全图测试，需要把四图和旋转设置写清，不能只运行一图便说完成。

实施时要求 Agent 保存有效成果，先追踪现有结构的职责，再改变必要部分。小问题优先小范围修复；跨模块矛盾则可以授权系统性调整，但要明确不应失去的行为和验证指标。

## 4. 用观察替代含糊评价

比“太慢了”更有效的反馈是：“21 分钟已经满人口，26 分钟才出发；第三波已清理，单位在主城等待；请检查出发条件是否被一个永远不满足的计数阻塞。”

报告问题时提供地图、模式、时刻或帧数、单位行为、资源和日志。把观察和猜测分开，例如“我看到矿工反复穿过主城”是观察，“黄金收入导致造兵慢”是待确认假设。这样 Agent 可以追到代码，而不是照着用户猜测随意改。

## 5. 一次改动对应一个解释

村民空闲不一定来自人数不足；可能是任务取消、资源占用、指令覆盖、携带放置或路径不可达。先画出状态转换，再找取消任务的入口。修好之后检查农田建造、采金和伐木是否仍正常，而不是只看一个角色标签消失。

反攻慢也不一定因为兵少：出发条件过严、错误探索、增援绕行、边界来回移动和转化中断都会浪费帧数。以端到端完成时间衡量修改，而不是只看局部指标变好。

## 6. 先验证构建，再验证行为

构建确认的是“源码能被目标工具链接受”，运行确认的是“策略能正确工作”。两者分别记录。Windows 本地 Debug 成功不能替代服务器 Release 测试；最终提交必须同时核对头文件与源文件、工程接口和命令提交协议。

测试矩阵建议固定四张地图和旋转，保留胜负、帧数与阶段信息。评测服务器有随机性时重复几次，并分别报告最好、平均和失败情况。当前公开数据仅能说明 11 条学校记录中 9 次胜利，不能替代完整覆盖报告。

## 7. 收尾也属于工程任务

代码提交后整理报告、结果、限制与复现步骤。报告中的个人信息应由本人提供；不确定的数据应问清或标记未知。把 AI 对话高度概括为需求分析、方案比较、实现检查和测试反馈，可以提高可读性，但不能把没有做过的实验写成已完成。

公开时使用干净目录，排除个人报告、原始日志、聊天截图、本机配置、编译产物和密钥，保留原作者许可证和必要资源。说明谁提供框架、谁设计策略、哪些结果有证据；完整项目和学校允许提交的两份文件应清楚区分。

## 学生真正需要做的事

- 读懂规则并选择策略：何时扩张、什么时候出发、何时允许祭司冒险。
- 看运行并提供证据：空闲农民、塔战损失、祭司后退等现象不能只靠 Agent 自己猜。
- 核对修改：比较需求与实际代码行为，确认改动没有破坏已有效的经济和防守。
- 做复现和解释：能指出数据结构、决策入口、失败恢复和测试口径，准备课程答辩。

这些参与在本项目的反馈中都真实存在，无须通过虚构“独立完成全部代码”来体现贡献。使用 Agent 的价值是扩大可处理的问题范围，而理解、验证和承担最终判断仍是学习的核心。
