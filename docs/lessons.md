# 问题复盘与课程项目经验

## 资源库存不是发展速度

反复出现过“木材很多、食物不足”“食物很多、黄金不足”“早早满人口仍迟迟不出发”。这些现象说明单个计数无法代表系统健康。应把时间拆成食物/黄金到位、时代前置、生产队列、兵力集结、行军、接敌、拆塔和转化，找出最长或被阻塞的环节。

采金远、放置堵塞时，增加矿工可能进一步拥堵；先造就近仓库、分离道路往往更有效。只围绕一个谷仓无限造田，会让边缘农田放置距离增长；多个小组与可用通道比外观整齐更重要。靶场也要在军队大量生产之前建设，避免资源到位后仍只能靠一个队列慢慢出兵。

## 角色切换不等于工作失败

村民在采集、携带、放置和返回途中会改变状态。如果每次标签变化都重新派工作，就可能让有效任务不断重启。另一个问题是多人反复争同一资源目标，或者错误把其他工人的进展当成当前工人的进展。

更合适的停滞判据应结合位置变化、携带变化、自己的有效目标和持续时间。重分配要有条件，也要给刚发出的动作留出执行窗口。建造 99% 的农田被经济重调度抢走工人，是模块之间缺少任务保护造成的问题；只“再派一个工人”可能掩盖同一根因。

## 不能把看不见当成已经消灭

战斗中敌军暂时离开视野，主力可能误以为附近没有目标，转身探索别处。塔数也有类似问题：屏幕上只有两塔，不代表全图只剩两塔。敌情记忆必须区分已观察、当前可见、确认死亡/转化与暂时失联。

路径既要利用对位信息减少搜索，也要验证实际可达性。河边直线移动无法跨过去时，反复下同一个移动命令没有作用；正确路径和沿路接敌状态需要一起处理。

## “更安全”也可能更容易超时

等过大的第一波兵力、增援一直等祭司带队、每次友军减少就让祭司取消转化，都有局部合理性，但会增加终局帧数。另一方面，兵力太少、增援逐个送入多塔火力、祭司过早冲进敌军，同样可能失败。

取舍应围绕实际目标：第三波防守后合理出发，前线维持有效输出，收尾以转化触发胜利。需要把“保护祭司”写成对真实危险的判断，而不是无条件后退；把“等待集结”写成有上限的策略，而不是任何时候都等待。

## 同一单位的命令需要仲裁

弓兵已经开始攻击却被移动重新覆盖，近战继承远程站位而不前进，新兵快到主力时重新绕路，都是多个决策同时控制一个单位的结果。应明确阶段和意图的优先级，识别命令是否仍有效，再决定是否重发。观察到“站着不动”时先检查它是否有攻击目标、射程和路径，而不是立刻增加移动命令频率。

## 编译兼容是独立问题

定点数与浮点数混用、函数签名差异、提交协议变化可能在服务器上直接失败。应读取接口实现，记录真实返回编号和反馈，保留目标 C++ 标准；不能因为旧 exe 跑得好就推断上传源码能编译。

Qt 的运行资源按工作目录读取。禁用影子构建可能偶然解决路径问题，但更准确的做法是明确工作目录、资源和 DLL 搜索路径。构建错误、启动错误、崩溃、超时和祭司死亡必须分别分析。

## 怎样把 AI 用成工程助手

有效的循环是：提出目标和边界 → Agent 读代码 → 形成假设 → 实现 → 验证 → 学生提供运行证据 → 修正。用户不需要逐行指定代码，但需要准确描述行为、判断策略取舍，并检查 Agent 是否偏离目标。

“不要破坏已有成果”应转化为具体清单，例如保留采金巡视、农田施工保护、第三波防守和转化连续性。有基线才能知道一次修改是否真正改善。发现多模块相互冲突时，可以授权整体调整，但仍需保存旧结果和逐项核对行为。

## 对学习的影响

这类项目让 C++ 的结构体、容器、继承、虚函数与生命周期问题落到真实系统里：SN 与数组下标的区别对应身份与存储位置；跨帧状态对应对象生命周期；资源预算对应多项决策的协调；指令反馈对应异步结果处理。算法正确也不够，还要处理它与单位状态、路径和时间限制之间的关系。

学生的贡献不仅是敲代码，也包括读懂规则、提出可测量的问题、选择发展与战斗方向、运行实验、比较结果和整理经验。Agent 可以加速搜索与实现，但如果不知道哪些指标可信，就容易把局部改善误判成全局提升。本项目最终的经验是：让每个修改都有证据和明确目的，让最终结果能够被他人复现和解释。

## 答辩时建议能回答

1. 为什么消灭所有敌方单位还不算胜利？
2. 一条指令从决策到执行经过哪些对象？反馈编号如何关联？
3. 为什么不能把快照数组下标保存到下一帧？
4. 村民空闲有哪些不同原因？如何区分放置途中与真实停滞？
5. 资源已经很多，为什么出兵仍然慢？
6. 河流与敌方活动范围如何改变路径和站位？
7. 祭司什么时候保守、什么时候接近转化？如何确认剩余塔数？
8. 公开评测结果能够证明什么，又不能证明什么？

回答这些问题比记忆一组参数更有助于完成课程，也能让后续修改更有依据。
