# 一套从需求到完成项目的提示词

这里是从本项目提炼的**可复用模板**，不是聊天逐字稿。按阶段使用，把 `<…>` 换成你的项目事实；不要一次把所有提示词都塞进上下文。每次说明当前目标和允许的检查范围，Agent 应读取真实文件后再决策。

## 0. 首次接手：先了解，暂不编码

```text
这是一款 C++/Qt 即时战略课程项目，路径为 <项目目录>。
允许修改的文件只有 UsrAI.cpp 和 UsrAI.h，不允许修改引擎、地图和评测参数。
目标是在规则允许的范围内自动获胜，并减少通关帧数。
先不要写代码，请阅读项目文档、AI 基类、游戏状态、指令执行和胜负判断。
请给出：项目运行流程、可用接口、胜负条件、经济/科技/作战约束、关键文件入口。
把已确认的事实和还需验证的假设分开；不要根据同名商业游戏推断这里的规则。
```

## 1. 形成整体设计并记录

```text
基于刚才的代码阅读，为玩家 AI 制定完整方案。
方案覆盖资源巡视、村民分工、建筑布局、时代科技、生产、防守、反攻、增援和最终转化。
为各模块写清输入、状态、优先级、共享预算、超时恢复和成功条件。
说明最容易互相干扰的部分，例如造田与升级争夺资源、移动指令覆盖攻击。
把规划写入 <允许保存规划的文档>，包含实现顺序和每一步的验收方法。
先完成文档，不要修改策略代码。
```

## 2. 按规划完成实现

```text
按照规划完成代码，修改范围仍然只有 UsrAI.cpp 和 UsrAI.h。
保留框架规定的类和提交接口。跨帧使用 SN，不保存会失效的快照引用或数组下标。
统一资源预算和单位指令仲裁，避免各模块重复分配同一工人或覆盖同一单位的有效动作。
优先形成可运行闭环，再完善异常恢复。读取执行代码确认建造、科技和转化的真实条件。
本轮允许 <只编译 / 编译并运行指定地图>，不要扩大检查范围。
完成后说明改动、验证结果和剩余限制；未经验证的性能不要写成结论。
```

```text
请从整体资源需求、生产能力和道路拥堵分析，不要只增减一个工种人数。
确认采集、携带、放置、建造、资源耗尽和空闲各状态的处理。
按规则安排就近放置点、农田分组和生产区。保持已经有效的防守与命令反馈逻辑。
列出拟修改模块及理由，然后完成必要实现和 <允许的检查>。
```


## 5. 检查农民反复换角色或空闲

```text
我看到部分工人停在树旁，村民/樵夫状态反复变化，或农田建到接近完成就无人施工。
请不要仅凭角色标签判定工人失效。检查目标是否耗尽/被占用，路径和携带是否有进展，
是否有同帧重发指令、任务取消、放置目标失效或施工被采集分配打断。
给有效任务留出完成窗口；只有确认停滞才重分配。
检查修复是否同时保持采金、农田补充和就近放置正常。本轮 <允许的检查>。
```

## 6. 调整反攻与接兵

```text

敌方基地优先对位定位，但必须使用可通行路径，处理河流和地形。
依据本项目射程与敌军活动范围安排近战前排和弓兵输出，不凭印象判断射程。
把出发、接敌和增援各自的阻塞条件说明清楚，完成必要修改并 <允许的检查>。
```

## 7. 处理最后拆塔与转化

```text

```

## 14. 上下文中断后的续做

```text
继续当前任务，不重新开始。先恢复已完成项、当前文件状态、约束、最近有效基线、
尚未解决的问题和已经允许的检查。必要时读取规划与日志。
本次新增要求为 <新的观察或约束>，它不取消原目标。
完成后以结果为主，说明本轮实际验证了什么，不重复已经完成的准备工作。
```

## 一次有效反馈的最短结构

```text
目标：<要改善的结果>
观察：<具体事实 + 发生设置>
边界：<允许改什么 + 必须保留什么>
验证：<本轮允许如何检查>
输出：<希望拿到代码、结果表还是分析>
```

提示词的价值在于减少信息缺口。写得长并不自动更好；把当前目标、事实、边界和验收方法说清，比反复强调“你认真一点”更有用。
